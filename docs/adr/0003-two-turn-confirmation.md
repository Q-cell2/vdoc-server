# ADR 0003：高风险修改的两轮确认

状态：已采纳（2026-10-16）

## 背景

语音场景没有确认对话框。删除表格、全文替换这类修改一旦执行，代价很高。通过解析转写文字来判断"用户说了好"，会依赖语言，也容易误判。

## 决定

高风险调用第一次出现时不执行，返回"请先询问用户"，并记下这个请求的指纹（工具名 + 去掉 id 和版本前置条件后的参数）。只有在**之后的轮次**（用户又说过话）里，模型重复了**同一个**请求，才放行并消耗这条确认。

## 结果

- 与语言无关，不需要解析转写。
- 文档在两轮之间变了、参数不同时，会重新询问（偏保守）。
- 模型的指令中写明了这条规则。

## 修订：确认之后必须有用户输入（2026-10-20）

"后面的轮次"不能证明用户说过话：vRealTime 在模型自己开口（`response.start`）、晚到的工具结果、没有当前轮次时收到的工具调用这几种情况下也会开新轮次。模型可以在这样的轮次里重发同一请求，消耗确认。

现在实时适配器统计每个会话的用户输入次数（提交音频、发送文字、提供方自己的语音结束检测；不统计转写，因为晚到的转写属于更早的发言），审查工具调用时一并传入。确认只有在**问过之后用户又有输入**、且在后面的轮次里重发同一请求时才放行。

- 仍与语言无关，不解析转写，也不判断用户说的是"好"还是"不"；这条规则防的是模型没等用户回答就自行重试。
- 计数在内存里，运行时重启后从 0 开始，此前记下的确认会重新询问（偏保守）。旧快照里没有计数的确认同样重新询问。
- 噪音触发的语音结束检测也算一次输入；这是语音场景下不解析内容的代价。

## 修订：聚合持有输入序号（2026-10-22，#38）

`RecordUserInput.execute` 将输入通知变成聚合命令。`VoiceSession` 持久化单调递增的
`userInputs`，待确认请求保存询问时的序号。`ReviewToolCall` 不接收外部计数，聚合
自行判断“不同轮次且输入序号更大”。适配器只报告提交音频、发送文字和语音结束事件。
这些通知与工具审查使用同一命令队列，输入写入失败时不会凭适配器内存放行。

上述决定替代 2026-10-20 修订中的适配器内存计数。对象重建后，序号和待确认请求
共同恢复，既不会无输入放行，也不会因计数清零而丢失已经收到的确认输入。
旧快照没有输入序号时从 0 开始；没有询问时序号的旧确认仍会重新询问。原有领域
快照只保存业务状态，审计身份和 outbox 放在应用层持久化 envelope 中。
